# 质量门槛

全部通过后才能作为完整报告交付。任一阻断项失败，先修复；若暂时无法修复，只能生成标题和结论均明确标注的“部分草稿”，不能把降级当作完整交付。

## 1. 输入门槛（阻断）

- [ ] ID 层级数据和名称对照数据都已提供，且有表头和有效行。
- [ ] 两个报表都已切换为本次目标客户；客户/集团名称只作标题，不与 `shop_name` 比对。
- [ ] 已取得一个准确报告周期，并同时用于客户货盘与营销参谋。
- [ ] 金额沿用内部报表原口径，不改写、不换算；无明确统一口径时分国展示。
- [ ] 少量明显损坏的 `product_id` / `shop_id` 行已隔离；其余核心 ID 可用。
- [ ] 必填字段完成显式映射；缺失值没有被静默填零。

## 2. 数据门槛（阻断）

- [ ] 所有经营计算只来自 ID 层级数据。
- [ ] 名称表重复行没有复制 GMV、消耗或曝光。
- [ ] 事实粒度为 `country × shop_id × product_id`。
- [ ] 重复事实行已加总有效 GMV/消耗；ROAS 只使用 GMV 与 cost 同时有效的同行数据重算，并披露覆盖率。
- [ ] 店铺名称变化始终以 `shop_id` 校准，商品名称变化始终以 `product_id` 校准。
- [ ] 指标能回溯到输入行；国家/币种未被错误合计。
- [ ] 消耗低于 0.01 的 ROAS 已标为低消耗方向性信号，未作为强品的单独依据。
- [ ] 商品行与店铺汇总使用同一 `country + shop_id` 标准展示名，其他名称只作别名。

## 3. 策略门槛

- [ ] 已生成 `plan-evidence.json` 并通过 `scripts/validate_plan_evidence.mjs`；GMV 守恒、占比和商品原型数量可复算。
- [ ] 默认给出三个差异清晰、证据充分的精品店方案；不足三组时有明确解释。
- [ ] 每个方案都写明承接店、主题、现有好品组合、重组证据，以及绑定在本方案内的营销参谋补品。
- [ ] 若大部分核心 GMV 或商品原型已在承接店，方案已标为“精修型”并默认降级；没有把低迁移价值包装成高价值重组。
- [ ] 所有重组型默认排在精修型之前；精修型例外前置仅使用主题纯度、经营强度或落地可行性的结构化理由，没有靠正文措辞绕过。
- [ ] 每个主题内商品服务同一用户/场景，不只是类目名称相近。
- [ ] 没有给商品强行分配店内角色。
- [ ] 没有把 Top 商品加总称为客户整体 GMV、大盘或市场份额。
- [ ] 固定事实区没有散落达人、直播、货品打法等自由发挥；所有 AI 因果解释集中在文末 `AI 延伸建议｜供客户评估`，并按三个方案分开。

## 4. 商品建议门槛（阻断）

- [ ] 报告没有规定最终主推款数量、SKU 数、具体尺寸、功率档位、价格档数或套装数量。
- [ ] 报告没有出现“只保留 1 个”“最多保留 3 档”“保留 1–2 个规格”“先上 4–6 个”等硬性指令。
- [ ] 同质品只做重叠提示，并将最终组合交给商家结合库存、毛利、供应链、内容和履约评估。
- [ ] 客观统计的候选条数与来源店铺数没有被误删；禁止的是处方性数量，不是事实数量。

## 5. 营销参谋门槛

- [ ] 已生成结构化 `gcrm-evidence.json`，并通过 `dependencies/gcrm-core/validate-evidence.mjs`。
- [ ] 每个实际输出的精品店方案都有至少一次成功的营销参谋查询；成功查询的 `theme_rank` 连续覆盖 1 到实际方案数，`theme_name` 与报告一致。
- [ ] 营销参谋状态来自证据验证器，而不是模型自行选择 `verified`、`no-candidate`、`unavailable` 或其他模式。
- [ ] 所有计划查询都真实执行并为 `success`；`not_attempted`、授权/登录失败、能力不足、筛选控件失败、用户跳过和 `unavailable` 只能生成部分草稿。
- [ ] 使用本地已登录浏览器；没有把找不到另一个 Skill 或云端浏览器授权当作跳过理由。
- [ ] 查询国家、一级/二级类目状态和精确周期均可见。
- [ ] 每次查询都有筛选后的 URL、含时区采集时间、实际读取行数、采集方式，以及截图/DOM 快照/导出证据引用。
- [ ] 补品发生在主题确定之后，且只补结构性缺口；没有强行凑数量。
- [ ] 每个确定补品有 `product_id`、原始标题、简洁中文名、营销参谋原 Shop Name、国家、一级/二级类目状态、统一报告周期、总 GMV、涨幅、平均客单价、广告消耗区间、TR（估）、渠道区间、图片或截图、筛选 URL 和采集时间。
- [ ] 原店铺名按营销参谋页面原样保留，可用于回到榜单定位原品；缺失时已标为“待定位”，未作为完整推荐。
- [ ] `verified` 的候选数直接来自证据文件，且每个补品都有真实图片，不用空图或“图片占位”通过。
- [ ] `verified_no_candidate` 有真实筛选条件、筛选 URL、采集时间、读取行数、查询证据引用和逐次未入选原因。
- [ ] 无登录/权限、控件失败或能力不足时状态为 `partial`，完整报告 QA 不通过；没有将这些问题伪装成“无合格候选”。
- [ ] `capability_blocked`、`filter_failed` 或 `unavailable` 已在 `browser.attempted_paths` 记录至少两条自动恢复路径；逐组人工筛选、交接用户或“请用户切好后回复”不算恢复路径。
- [ ] 标题匹配没有被冒充为 `product_id` 确认。
- [ ] 区间保持原样；`TR（估）=广告消耗区间中点÷总 GMV 区间中点`，推导值与证据一致。无法形成中点时写“不可计算”并说明原因。
- [ ] 超过 300% 的增长有低基数/活动/短期爆发提醒。
- [ ] 部分草稿没有出现伪造的营销参谋数据，也没有被称为完整报告。

## 6. 文档门槛（阻断）

- [ ] 标题下第一屏显示唯一准确报告周期、生成日和识别国家。
- [ ] 核心结论位于 Top 3 之前，统一落地逻辑全文只出现一次。
- [ ] 每个方案内先展示现有好品，再展示本方案营销参谋补品；补品标题后紧跟用途说明，没有把三个方案补品堆成全局列表。
- [ ] `AI 延伸建议｜供客户评估` 是最后一个章节，方案 1、2、3 分开，固定事实不依赖该章节才成立。
- [ ] Top 3 汇总表与分店明细的 GMV、ROAS、来源店铺数能对上。
- [ ] 飞书 Top 3 总表按不超过 6 个信息列分组，关键数据合并展示，判断列足够宽；没有因窄列逐字换行产生异常大空白。
- [ ] 每个金额/比率的覆盖范围清楚，店外候选占比没有被写成客户整体占比。
- [ ] 每个补品保留标题和独立商品图，证据按“商品定位、大盘表现、投入与渠道、补品判断、数据来源”分组；没有退化成一条竖线分隔的长段落。
- [ ] 飞书图片可见、链接可点击；不可写飞书时已提供信息与证据完整的可编辑替代版本。
- [ ] 文档已读回检查，关键表格、图片、链接和时间窗口没有丢失。
- [ ] 交付前运行 `node scripts/validate_report.mjs --report <报告> --report-window <起止> --generated-date <日期> --plan-evidence <方案证据.json> --gcrm-evidence <营销参谋证据.json>`，结果为 `delivery_status=complete`。

## 7. 安全门槛

- [ ] 公共仓库不包含客户原始数据、带真实客户身份或真实 19 位 ID 的报告/截图、Cookie、Token 或其他凭证；通用说明图片和任务所需内部入口可以保留。
- [ ] 内部入口没有被描述为公开访问权限。
- [ ] 输出分享范围符合使用者所在组织的数据分级要求。
